## What changed in revision 2

| Revision 1 | Revision 2 | Why |
|---|---|---|
| One number (dollars per correct finish) decides | Separate columns, and an order for deciding written before any run: safety and honest reports, then successes, then cost per success, then time | One number let a slower or less reliable arm win |
| 1 run per arm, top-ups only on close results | 3 runs per arm on every case, no selective top-ups | One lucky run could justify a deletion |
| Cases where both arms fail are left out; cases one arm never passes are kept out of the mean | Every case counts. Cost per success is all valid spend divided by all successes, so a task that goes from 0/3 to 3/3 counts for the arm that solved it | The old rule could make the plugin lose a task it won outright |
| "The run has an error" voids it | Only machine faults void a run. Timeouts, running out of turns and wrong finishes are failures, and their cost counts | Dropping the agent's own failures rewards unreliable approaches |
| Both arms fail means the case is broken | Each case ships a known-right and a known-wrong solution, and a unit test proves the hidden checks tell them apart, before any paid run | A hard task is not a broken one |
| Remove whole hooks that tie on five short tasks | Count what each hook prints from transcripts already on disk ($0). Trim printed lines, not scripts. Keep a recovery part unless a scenario actually triggers what it prevents | A hook that prints nothing costs no quota, and short tasks never interrupt, compact or resume |
| "continue", "try again", "whats left" all arm keep-going | Status questions never arm. Resume words arm only on an open run with a Done when and an open task. "Try again" restores the keep-going state from before the stop, and never creates one | A status question is not permission, and a project's broad purpose is not a finish line |
| Repeated questions and parked decisions can't be benched | One scripted multi-turn scenario: an interrupted build, resumed by "continue", with an answer sheet for questions. It counts nudges and re-asked questions | The eval does one turn, but a script can do several |
| One table or picture per status report | Dropped. Communication is judged on the last message: a clear recommendation, honest uncertainty, no asking for what is already known. It is reported, not used to decide | A fixed ritual is what this plan removes elsewhere |
| Guard refusals rewritten as bare facts | A refusal keeps what was blocked and the way through, written as a fact | Removing the remedy causes retries |
| `--model opus`, eval exit code fails the job | Full model IDs for agent and judge, `--ablation` always explicit, eval exit codes 1 and 2 still go on to grading | Aliases drift; failing cases are expected |
| ~$120–250 | ~$250–500 list price on Opus (below) | Top-ups were understated; three arms, a scenario and held-out cases added |

## The goal and what gets measured

The owner's goals: more correct work done sooner; more done per unit of plan
quota; Claude acting as the senior engineer, so the owner reads plans, short
status lines and pictures, and talks it through.

Each comparison reports these columns per arm:

| Column | What it is |
|---|---|
| Successes | Runs where the hidden tests and every deciding grader pass, out of all valid runs, per case and in total |
| Cost per success | All list-price spend on valid runs, divided by total successes. The eval's own cost includes judge calls, so execution cost comes from `measureTree` over the kept transcripts |
| Median time | Seconds per run |
| False "done" | Runs whose last message says the work is finished or ready while the hidden tests fail |
| Nudges | Multi-turn scenario only: the "continue" messages the script had to send before the work passed |
| Re-asked | Multi-turn scenario only: a question asked again after the answer sheet answered it |
| Communication | An LLM judge (pinned model) on the last message: a clear recommendation, honest uncertainty, plain words, no asking for what the workspace already says. Reported only, never deciding |

List-price dollars are a stand-in for plan quota, not a measure of it. Release
notes say "cheaper at list price", never "more work per subscription".

## The rule, written before any run: `bench/RULE.md`

**The incumbent** is what is shipped or on the branch now. **The candidate** is the change.

- **Runs:** 3 per arm on every case, with arms that are compared run together in one job, never on different days.
- **Valid run:** any run except one stopped by a machine fault: runner crash, credential rejected, usage-limit text, scaffold failed, left unstarted when the eval exits 2, or a trace that reads `bench-hidden/` or the copy's `bench/`. A voided run voids its pair in the other arm.
- **Failure:** a timeout, running out of turns, or a wrong or unfinished result. Its cost counts.
- **Decision order:**
  1. **Gates.** The candidate has no more false "done" runs than the incumbent, and removes no safety stop (guard-bash, the stop-and-ask rules). Fail a gate and it loses.
  2. **Successes.** Fewer total successes and it loses. If a single case has fewer successes, both arms get 3 more runs on that case together. If it is still fewer, the candidate loses. Extra runs can only stop a change, never approve one.
  3. **Cost per success.** At or below 0.85× the incumbent's is a win on cost. At or above 1.15× is a loss.
  4. **Time.** A candidate whose median is more than 25% slower needs a written reason to ship.
- **Clear win:** passes 1 and 2, and either has at least 2 more successes in total, or wins on cost, with time within the limit or a written reason.
- **Inconclusive** (anything that is neither a clear win nor a clear loss): a wording simplification ships, because simpler is cheaper to read every session. A removed capability stays. An addition does not ship.
- **Stop-loss:** each batch's `--max-cost-usd` is written here before it runs. With `-j 2` the eval can pass it by up to two runs, because runs already started finish.

## Stage 0: fixes held by unit tests (no bench runs; building them uses session quota)

1. **Resume words keep Claude going on a real goal.**
   - Three intents, kept apart in `lib/persist-words.mjs`:

     | Intent | Words | Effect |
     |---|---|---|
     | Status | whats left, what's left, where are we, status (with or without "?") | Never arms |
     | Resume | continue, resume, carry on, pick up, go on, keep going, "lets resume" | Arms only on an open run (below) |
     | Retry | try again | Restores the keep-going state that was on before the stop. Never creates one |

   - A resume or retry prompt is 12 words or fewer, has no new-goal verb (`NEW_GOAL_VERB` in `lib/resume.mjs`), and has no don't, do not, stop, wait, hold, pause or no.
   - **Arming gate:** `readGoal(...).source === 'ledger'`, the run's Done when is filled in, and at least one task is not done. The project page's "What this is for" is a purpose, not a finish line, so it never arms keep-going. `readGoal`'s fallback chain stays as it is, because the goal line shown after a summary still needs it.
   - The explicit "until done" path keeps its goal logic, except that the phrase itself ("continue until complete") is never saved as the goal.
   - Where the goal came from is stored, which ends the two-goals split at `persist-check.mjs:286`.
2. **The Stop block names the next open item.** `nextOpen(runText, projectText)` in `lib/runs.mjs`, built after reading that file's task states:
   - done tasks are skipped;
   - a blocked task is shown as "blocked on …";
   - Pickup is used only when it is newer than the last task change;
   - then the first item in PROJECT.md's Next;
   - every task done gives its own state: "all tasks done; the done-when has not been checked", which is not a reason to keep going with filler.
   - The block shows `next open item: <≤120 chars>` in place of the bare "step N of 25".
3. **Hook notes state facts.** The persist-check resend note, checkpoint and commit lines; the context-check hand-back note ("Last hand-back N bytes; it is re-read every later turn.") and leftover-files note; workers `cappedNote`; recover `unreturnedNote`; turn-check's blocks; the router's usage lines and `leadNote`; resume `handoffLine`; the Monitor sentence. Guard refusals wait for Stage 2.
4. **Hook count pin:** `docs-drift.test.mjs` checks SKILL's "Eight hooks run around you" against the distinct scripts in `hooks.json`.
5. **CI runs every test.** `ci.yml` runs `node scripts/test.mjs` after the package step, and `collectTestFiles` picks up `evals/*.test.mjs` and `bench/**/*.test.mjs`.

**Tests:**
- Resume arms: "resume", "continue", "yes continue", "continue whenever your ready", "carry on", "ok lets resume".
- No arming: "whats left", "whats left?", "where are we?", "continue and add a login page", "no, don't continue", a bare "continue" with no run, and "continue" when every task is done.

## Stage 1: the bench, and the check on its checks

**Owner steps** (credentials, so I cannot do them): run `claude setup-token`, then `gh secret set CLAUDE_CODE_OAUTH_TOKEN --repo 1xmint/orchestrate` and paste the token. The token never passes through me.

**Layout** (dev-only, not part of what users install):
- `bench/<case>/{case.yaml, prompt.md, graders/, fixture/}`, run with `--eval-dir bench`.
- `bench-hidden/<case>/{*.test.mjs, must.json, right/, wrong/}`: hidden tests on `node:test` only, plus a known-right and a known-wrong solution.
- `bench/grader-check.test.mjs` (in CI, $0): for every case, the hidden tests pass on `right/` and fail on `wrong/`.
- `bench/make-copy.mjs --arm <name> --out <dir>` builds a plugin copy outside the repo, never including `bench-hidden/`.
- `bench/hook-bytes.mjs` ($0): reads transcripts on this machine and prints per-hook totals only: number of injections, bytes, and Stop blocks raised. It prints no text from the transcripts.
- `evals/grade-kept.mjs`, pure functions behind a thin command line:
  - `readRuns` reads the aggregate result;
  - `workspaceOf` finds the kept workspace;
  - `validity` applies RULE.md;
  - `runHidden` runs the hidden tests on a copy of the workspace, with a timeout;
  - `execUsd` measures the transcripts;
  - `table` prints the columns above.
- `.github/workflows/bench.yml`:
  - **Trigger:** `workflow_dispatch` only, with `permissions: contents: read`.
  - **Matrix:** the arms of one comparison as matrix legs, started together.
  - **Machine:** `ubuntu-24.04`, a 350-minute timeout, Node 22, and the Claude Code version pinned to the one this machine runs.
  - **Shell sandbox:** bubblewrap and socat, plus the user-namespace sysctl.
  - **Eval call:** `--model claude-opus-5-5`, `--judge-model` set to a full model ID, `--ablation` always explicit, `--no-publish`, `--keep-temp`, and a `--max-cost-usd` stop-loss.
  - **Exit codes 1 and 2 are expected.** The step records the code and the job goes on to grading.
  - **Hidden tests:** `bench-hidden/` is moved out of the tree while the eval runs.
  - **Leak scan:** every file about to be uploaded is searched for the token's value, and the job fails without printing anything if it is found.
  - **Upload:** the aggregate, the report, the table and the traces only, kept for 7 days. Never the eval's temp home.
  - **Secrets:** `ANTHROPIC_API_KEY` is never referenced.
- A STATE.md decision records why this fits AGENTS.md's "nothing that bills an outside service or needs its own API key": the job is dev-only and started by hand, it uses the owner's subscription, and Actions are free on a public repo.

**Multi-turn scenario** (`bench/scenarios/resume.mjs`, headless `claude -p --resume` driven by a script):
- Turn 1 gives a five-part build with a Done when.
- The first session is cut off by a turn limit to stand in for a usage-limit stop.
- The script then sends "continue" until the hidden tests pass or five nudges have been sent.
- One planted question has its answer on the answer sheet. The script answers it once. Asking it again counts as re-asked.
- Arms: no plugin, v0.21.0, and the branch.
- Compaction: the pilot checks whether a summary can be forced in headless mode. If it cannot, context-check and postcompact are recorded as untested and kept.

- The leak scan fails on a planted fake token.
- The sandbox runs on the runner.

## Stage 2: one principle for helpers (built before the first paid comparison)

**Card paragraph 3** (`lib/card.mjs`; the card stays under 2,200 characters):

> Do the work yourself unless a helper is expected to lower the total cost of a correct finish, counting the brief, the return you keep, checking and retries. Reasons to consider one: it keeps a large read out of your context, independent parts can overlap, mechanical work has a cheap check of correctness, or a review covers a specific costly risk. If the user asks for a helper or a model, use it. The plan the user sees is Next in .orchestrator/PROJECT.md; keep it current. Builders: orch-implementer on sonnet, own worktree (worktree: yes); finders: Explore on haiku, orch-researcher on sonnet. Tell the user "helper folder", never worktree, harness or a role name.

## Comparisons, in order

1. **Pilot** (above).
2. **Comparison A:** no plugin, the branch with Stage 0 ("current"), and current plus Stage 2 ("proposed"), all on the five cases, 3 runs each, run together. Recorded in `docs/research/0010-bench-a.md`. RULE.md decides proposed against current, and the plugin against no plugin is reported.
3. **Scenario:** no plugin, v0.21.0 and the chosen version, 3 runs each. Recorded with the nudges and re-asked columns.
4. **Trim** (Stage 3):
   - `hook-bytes.mjs` ranks the printed lines by bytes per session.
   - For each costly line: if a case or the scenario triggers the failure it prevents and the line does not help there, it is removed. If nothing triggers it, it is made quieter (printed only when its trigger fires) or kept and labelled untested.
   - The trimmed version is compared against the untrimmed one on the five cases and the scenario, as one bundle. A bundle result says nothing about any single line in it.
5. **Autonomy fixes**, each built only when a case or the scenario fails without it, and each naming that case:
   - check each Done-when line before saying ready (ready-trap);
   - search the config before asking (look-first);
   - a helper commits a compiling checkpoint before its turn cap (three-tools);
   - no re-asking an answered question (scenario).
6. **Held-out check:** the chosen version against no plugin on the two held-out cases, 3 runs each. If it loses there, the release waits.
