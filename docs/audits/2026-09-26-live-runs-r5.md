# Live runs — round 5, the helper path forced (2026-09-26)

Round 4 (`2026-09-26-live-runs-r4.md`) ran a delivery big enough to need
helpers and the lead built it alone in 23 tool calls, so the plugin had still
never been seen dispatching a helper live on this machine. Round 5 runs the
same delivery against the audit branch at `b52b6af` (wave 6 landed) with one
change to the prompt: the user asks for helpers outright. That is not a test of
the card's helper rule — round 4 settled that the rule is followed by the
model, not enforced — it is the first live exercise of everything downstream
of a dispatch: the dispatch guard, the helper roles, their worktrees, their
returns, the command guard inside a helper, and the lead's integration of
three parallel results.

## Method

Same as round 4: the branch loaded with `--plugin-dir` from a detached worktree
pinned at `b52b6af` with both skill packages built, the installed copy disabled
for the child with `--settings '{"enabledPlugins":{"orchestrate@orchestrate":false}}'`,
`--model sonnet`, headless `-p`, `--output-format stream-json --verbose`,
`--max-budget-usd 10`, default permission mode (reported as `auto` in the init
event). The init event lists the plugin as `orchestrate@inline` version 0.16.1
with the eight agents. One fresh throwaway repo under a short temp path with
one empty commit; deleted after this write-up. The raw transcript, the app's
own session transcript and the three helper transcripts are kept in the
session scratch folder `live6/` (not committed: machine paths).

The prompt: the round-4 tool-library app (catalogue with a category filter, a
validated borrow form that refuses a tool already on loan, an admin page behind
a password from an environment variable; each part with its own tests on
Node's built-in runner; a README), plus: "Please do not write the three parts
yourself: hand each one to a separate helper, since they do not depend on each
other. When they are done, check their work, wire the parts together, and tell
me in plain words what the helpers did, what you checked, and roughly what it
cost. I will not be able to answer questions."

Settings file: modification time identical before and after (the same 12:25:42
stamp as round 4). Nothing on this branch touched it.

## What the hooks did

From the app's session transcript and the plugin's own state folder:

- The card was injected on the first prompt, as in round 4.
- The brief line, in its wave-6 wording, said the project has no "What this is
  for" section and named the template. No doubled path this time.
- The context line fired three times, at ~43k, ~58k and ~76k of ~200k.
- **The dispatch guard refused the first helper.** The lead's first dispatch
  was the app's uncapped `general-purpose` kind. The guard answered: "general-
  purpose has no turn cap and can start helpers of its own. Send a capped role
  agent instead: orch-implementer (model "sonnet") to change code, …". The lead
  re-sent the same brief to the plugin's builder role on the next call and
  never tried the uncapped kind again. First live sighting of this guard.
- **The command guard fired inside a helper.** The borrow helper ran a command
  block that contained an `rm -rf`. The guard refused the whole block: "This
  would permanently delete files or folders that cannot be recovered. Say yes
  to continue. If nobody can answer here, stop and tell the user what you were
  about to run instead of trying again. A background helper cannot ask, so
  this is refused; report back to the lead instead of retrying." The helper
  redid the copy without the destructive line and finished.
- **The wave-6 headless refusal fired on the lead.** At the end the lead tried
  to delete the helpers' branches and worktrees. The guard: "This would
  permanently delete a branch. You are in auto mode, where nobody can say yes,
  so this is refused: run it yourself in a normal session, or add the exact
  command to .orchestrator/allow-bash.json." The lead told the user, in plain
  words, that the leftovers are harmless and left them.
- The plugin left a context record for the lead (85,527 tokens, measured) and
  one for each of the three helpers, a session record, and a returns folder
  for the session: the stop hook filed the helpers' returns.
- No size notice, no compaction, no recover notice, no checkpoint: nothing to
  say, nothing said.

## The findings

**The helper path works live.** Three builders ran at once, each confined to
its own files and its own worktree, each committed on its own branch and
returned a written account of routes, files and test counts; the lead merged
the three branches, wrote the one shared file, ran every test and drove the
server by hand before reporting. That is the shape the plugin describes, seen
end to end for the first time on this branch, and both guards did their job
without a human in the loop.

**The lead never opened the skill, a ledger or a packet.** In a headless run
the card is the only plugin text the lead sees, and the card points at the
skill rather than requiring it. The lead's briefs to the helpers were good on
substance — the interface each module must export, the data-file contract,
the files each one owns — but had no done-when evidence line, no progress
file and no return schema, so the ledger, the progress files and the
return-filing rules were not exercised. What would have caught a bad return
was the lead reading every handler itself, which it did. This is the same gap
round 4 named from the other side: the method is followed by the model when
the model chooses to, not enforced.

**The lead's worktree instruction contradicted the role, and that cost about
a third of the run.** Each brief said "Work directly in the project root (do
not use a separate worktree) since other parts are being written there
concurrently." The builder role is isolated in a worktree by its definition,
and the harness refuses writes from an isolated helper to the shared checkout.
Two helpers noticed and worked in their worktrees. The third wrote its files
to the path the brief gave as `/tmp/...`, which in its shell was not the
Windows temp folder the lead meant, so the work landed in a folder outside the
repo; when the helper found its worktree empty it copied the files into the
shared checkout by hand. The lead then spent roughly 30 of its 115 tool calls
finding where three helpers' work had gone (`find / -iname borrow.js` among
them), copying and merging. Nothing was lost and the tests caught nothing
wrong, but the run took twelve minutes where the parallel build itself took
about four. Two causes, both fixable in text: the builder role does not tell
the helper that it always works in its own worktree and branch and must not
write to the lead's checkout, so a lead can instruct the opposite; and a
packet that names a path in one shell's spelling is read in another's on
Windows, which the packet template's `WHERE` field (repo, base, branch,
worktree yes/no) would have prevented had the lead used it.

**Cost.** $2.28 for a finished, tested, committed three-part app with no
questions asked, against $0.69 when the same lead built the same app alone in
round 4. The extra is the three helpers' own steps plus the integration
detour above. For a user whose scarce thing is quota, the alone build was
cheaper and faster here; the helper build is what scales when the parts are
too big for one context, and this run shows it working when asked for.

What it means for the audit: the coordination scores now rest on a live
transcript of this branch dispatching, guarding, collecting and merging, not
only on unit tests and reading. The still-unmeasured things are unchanged:
the eval suite, a triggering eval, a clean-profile install, and spend read
from the bill.

Small fix worth making: the builder and debugger roles should say where they
work — their own worktree and branch, never the lead's checkout — so a lead
cannot instruct the opposite and a helper does not hunt for its files.
