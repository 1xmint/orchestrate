# Live runs — round 6, the helper path after wave 7 (2026-09-27)

Round 5 (`2026-09-26-live-runs-r5.md`) showed the helper path working live
and named its one real cost: the lead told each builder to work in the shared
checkout, the builder role is isolated in its own worktree, and the run spent
about a third of its time finding where three helpers' work had gone. Wave 7
answered that in text and in a guard: the builder and debugger roles now say
where they work, and the dispatch guard refuses a packet that sends either of
them into the shared checkout. Round 6 runs the same delivery, with the same
prompt, against the audit branch at `923eb39` (wave 7 tracks A–E landed) to see
whether the detour is gone and what the new guard does when a real lead meets
it.

## Method

Same as rounds 4 and 5: the branch loaded with `--plugin-dir` from a detached
worktree pinned at `923eb39` with both skill packages built, the installed copy
disabled for the child with
`--settings '{"enabledPlugins":{"orchestrate@orchestrate":false}}'`,
`--model sonnet`, headless `-p`, `--output-format stream-json --verbose`,
`--max-budget-usd 10`, default permission mode. The init event lists the plugin
as `orchestrate@inline` version 0.16.1 with the eight agents. One fresh
throwaway repo under a short temp path with one empty commit; deleted after
this write-up. The raw stream, the app's own session transcript and the three
helper transcripts are kept in the session scratch folder `live7/` (not
committed: machine paths).

The prompt is round 5's, word for word: the tool-library app in three
independent parts, each with tests on Node's built-in runner, a README, and
"Please do not write the three parts yourself: hand each one to a separate
helper … tell me in plain words what the helpers did, what you checked, and
roughly what it cost. I will not be able to answer questions."

Settings file: modification time identical before and after (the same
12:25:42 stamp as rounds 4 and 5). Nothing on this branch touched it.

## What the hooks did

From the app's session transcript and the plugin's own state folder:

- The card was injected on the first prompt, in full (the prompt is long and
  full of build words, so the wave-7 short card did not apply). It appears once.
- The brief line said the project has no "What this is for" section and named
  the template. No path.
- The context line fired three times, at ~43k, ~51k and ~75k of ~200k.
- **The dispatch guard refused six dispatches before three launched.** The
  lead sent all three briefs at once as the app's uncapped `general-purpose`
  kind; the guard refused each ("general-purpose has no turn cap and can start
  helpers of its own. Send a capped role agent instead: orch-implementer …").
  The lead re-sent all three to the builder role, and the **new worktree
  guard refused each**: "orch-implementer always works in its own worktree and
  branch; a packet that sends it into the shared checkout makes it write
  outside the repo or refuse. Say WHERE: … worktree: yes and merge its branch
  when it returns." The lead put `WHERE: worktree: yes` at the top of each
  brief and re-sent; all three launched. Nine dispatch calls for three helpers,
  each refusal answered correctly on the next try, with no human in the loop.
  First live sighting of the worktree guard.
- **The worktree detour is gone.** Each helper's transcript shows every command
  run inside its own worktree; each wrote its files there, ran its tests there
  and committed on its own branch. No helper wrote outside the repo, none went
  looking for its files, and the lead's integration was three merges plus one
  scaffolding commit. Helper tool calls fell from 75 to 37, wall time from 717
  to 426 seconds.
- The command guard did not fire. Nothing a helper ran matched a rule (no
  `rm -rf` this time), and the one command the lead ran that should have been
  stopped was not covered: see the findings.
- The plugin left a context record for the lead (90,961 tokens, measured) and
  one for each helper (34,459, 38,182 and 35,305 tokens).
- No size notice, no compaction, no recover notice, no checkpoint.

## The findings

**The guard taught the lead the packet field it had never read.** In a
headless run the card is the only plugin text the lead sees. The lead's briefs
carried no `WHERE`, `DONE WHEN` or `RETURN` fields in the first six attempts.
The worktree refusal names the field and the value, and the seventh brief
opens with exactly that line. That is the refusal wording doing what wave 7
asked of it: the lead did not have to open the skill to recover. The rest of
the packet template still went unused, as in rounds 4 and 5, and nothing
enforces it.

**`taskkill //F //IM node.exe` went through the command guard.** To stop the
test server it had started, the lead force-killed every process named
`node.exe` on the machine. In this throwaway run nothing else of the user's
was running under that name, but on a real machine that line ends every Node
program the user has open: other servers, editors' language servers, other
Claude sessions' tools. It is destructive, it is not recoverable by undo, and
the guard has no rule for it: its destructive-command list covers deletion of
files, branches and history, not killing processes by image name. Fix: add a
rule for `taskkill /IM`, `taskkill //IM`, `pkill -f`, `killall` and `kill -9`
without a specific pid to the command guard's refusal list, with the helper
and headless wording the others use. That is the one change this round names.

**The last sentence of the report was wrong.** "I have not committed these
changes to git" is true of `server.js`, `README.md`, `.gitignore` and the
`package.json` edit, which were left unstaged, and false of the four commits
the lead made on master (scaffolding and three merges). A user who takes the
sentence at face value and runs a reset to "start clean" keeps the commits and
loses the server file. The plugin has no check on a claim about repository
state in a final report; the return-check hook looks at helper returns, not
the lead's message to the user. Worth a test-backed sentence in the card or the
skill's reporting section: say what is committed and what is not, from
`git status`, not from memory.

**Cost.** $1.81 for a finished, tested, mostly committed three-part app with no
questions asked, against $2.28 in round 5 and $0.69 when the same lead built
the same app alone in round 4. The saving over round 5 is the detour: the
helpers did half the calls and the run took six fewer minutes. The alone build
is still cheaper for a delivery this size; the helper build is what scales when
the parts are too big for one context, and this round shows it working without
the recovery cost.

What it means for the audit: the coordination scores now rest on two live
transcripts of this branch dispatching, and the second shows the fix for the
first's largest cost working. The safety score has a new measured miss (the
process kill). The still-unmeasured things are unchanged: the eval suite, a
triggering eval, a clean-profile install, and spend read from the bill.

## Erratum to the round-5 write-up

Round 5 reported "115 lead tool calls (Agent 4, Bash ~70)" and "roughly 30 of
its 115 tool calls" spent on recovery. That count included the helpers' calls;
the stream marks a helper's calls with the id of the dispatch that started it,
and splitting on that gives lead 40 (Agent 4, Bash 17, Write 7, Read 6, Edit
3, wake-ups 3) and helpers 75. The recovery cost was real but it was mostly
the helpers' (copying files by hand, searching the disk), not the lead's. The
comparison above uses the corrected split for both rounds.

One run, $1.81 of the $10 cap. Round-6 total spend on live runs: $1.81.
