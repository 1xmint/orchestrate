# Handover after 0.17.0 (2026-09-29)

For the first session that runs 0.17.0. Read this, then
`STATE.md` (the v0.17.0 entry), then work.

## Where things stand

- 0.17.0 holds everything from the audit run: about 85 commits after 0.16.1.
- The plugin's own tests pass. The last full audit score was 89 (round 10).
  Round 11 is partial: `docs/audits/2026-09-29-scoresheet-r11.md`.
- No further scoring rounds are planned. The scorer's spread was as large as
  a round's gain.

## What to watch in a real session

Each of these is built and tested and has not been seen live. Note what
happens the first time each comes up.

1. The first helper of the session: are three short lines written to the
   user first, and is a helper sent without them held back?
2. The recovery note after a summary: does it still list helpers that did
   return as "never returned"? Does the size line still say
   "newest checkpoint: none" after a summary? Both were seen on 0.16.1.
3. Tidy-up after helpers: do a merged branch and a clean folder go through
   first try? Does the leftover note arrive once, with a true count?
4. A discard of unsaved edits: stopped when there are edits, passed when not.
5. A short fix request ("fix login properly"): does a card arrive, and does
   the lead look for the cause before changing anything?
6. A helper's size note: does the helper carry on below its budget and hand
   back at it, without stopping early?
7. Work touching money or sign-in: is it held for review, and does a failed
   review keep the hold?

## Known limits

Listed in `STATE.md` under v0.17.0. The two largest: a helper cannot save,
compact and carry on, so a job larger than its room must be split before it
is sent; and the three largest hook scripts need a tidy that is about a day
of work.

## Lessons about the method

- Size a helper's job against the room it has left after its starting load,
  not against its whole budget. Required reading over about 30 KB means
  split the job.
- Send one helper first and read its return before sending several.
- Prefer a few helpers with room over many small ones; each pays a fixed
  starting cost.
- Do in rounds, with a summary between, what would otherwise run as many
  strong helpers at once.
- A new test is proven by showing it fails on the code as it was.
- Write the stop rule before the run starts.
