# Live runs — round 9, five scenarios against `cbad2b5` (2026-09-28)

Round 8 reached the parts of the plugin that only fire under pressure. Its
fixes landed: the per-segment turn count, the dispatch/return pairing, the
single resume rule, the unforced branch delete for `worktree-agent-*`. The
compaction gate was replaced by a checkpoint request in the context meter.
Round 9 runs the same four pressure scenarios again against the audit branch
at `cbad2b5`, plus the original delivery prompt (run 0), to see which of the
round-8 findings those changes closed.

## Method

The harness is the same as round 8:

- The plugin loads with `--plugin-dir` from a detached worktree pinned at
  `cbad2b5`, with both skill packages built (75 files each).
- The installed copy is disabled for the child with
  `--settings '{"enabledPlugins":{"orchestrate@orchestrate":false}}'`.
- The child runs `--model sonnet` headless (`-p`) with
  `--output-format stream-json --verbose` and `--max-budget-usd 10`, on Claude
  Code 2.1.274.
- No permission flag is passed. The stream's `init` event reports
  `permissionMode: "auto"` for all five runs: the profile's own default, read
  and not changed. Round 8 ran the same way.
- Each run gets one fresh throwaway repo under `<tmp>`, deleted after this
  write-up.
- Raw streams, the app's session transcripts and the helper transcript stay
  in the session scratch folder. They are not committed because they contain
  machine paths.

Three things differ from a clean run, and all three are disclosed because
they change what the numbers mean.

- **The implementer's turn cap was lowered from 100 to 20** in the live
  worktree's copy of `agents/orch-implementer.md`, for run 3 only. It was
  restored afterwards; a recursive diff of the live worktree's `skills/`
  against `cbad2b5` shows no difference.
- **Runs 2 and 4 set `CLAUDE_CODE_AUTO_COMPACT_WINDOW=100000`** in the child's
  environment.
- **The fixtures were rebuilt, not reused.** Round 8's throwaway repos had
  been deleted.
  - The 31 requirement files (run 1) were recovered in full from the Read
    results recorded in the round-8 streams.
  - The twelve 522-line meeting minutes (run 4) were recovered the same way,
    with no line missing.
  - The 12,001-line spec (run 2) was regenerated from its recorded pattern: a
    header, then 12,000 numbered filler paragraphs cycling ten topics, with
    four `HIDDEN REQUIREMENT` lines at paragraphs 1310, 4870, 8410 and 11605.
    It is 780 KB against round 8's 762 KB, and its head matches.

The settings file's modification time was identical before and after every
run (the same 12:25:42 stamp as rounds 4 to 8). Nothing on this branch
touched the real profile.

The five prompts, one line each:

0. **Delivery with helpers.** The tool-library app in three independent parts
   (catalogue, borrow form, password-protected admin). Each part goes to its
   own helper, built at the same time. Tests, a README, and a plain report of
   what the helpers did and what it cost. The user cannot answer questions.
1. **Requirements, one file at a time.** The same as round 8: a helper reads
   the 31 requirement files and reports contradictions; keep `notes.txt`.
2. **Hidden requirements in a long spec.** The same as round 8.
3. **One helper for the whole build.** The same as round 8.
4. **Twelve meetings, one decision each.** The same as round 8.

## What changed since round 8 that the runs show

- **Cap detection is fixed.** In round 8 a resumed helper that finished was
  still marked PARTIAL with a wrong turn count. This time there was no
  partial note after the resume.
- **Resume is now consistent.** The host's notice, the lead's action (one
  SendMessage) and the plugin all point the same way. The lead resumed the
  helper and did not redo its work.
- **The guard's refusal text for commands nobody can answer changed.** It now
  reads "The question cannot be answered here… report back what you were
  about to run". The helper did exactly that and found the safe form.
- **The checkpoint request moved from the PreCompact gate to the meter.** It
  still did not reach the lead: round-8 finding 4 is closed in the code but
  not in practice. The request missed by 96 tokens, because readings arrive
  in steps of about 38k.
- **The implementer worktree rule is new here.** It refused three dispatches
  in run 0 that did not say where to work. The lead fixed its packets and
  went on. This cost three lead turns.
- **Some round-8 findings are unchanged:**
  - The meter's window figure ignores the override (round-8 finding 7).
  - Started servers are left running in 2 of 5 runs, while runs 1 and 2
    stopped theirs (round-8 finding 5).
  - Helper branches and `.claude/` are left in the user's repo (round-8
    finding 6). The lead still reaches for the forced delete.

## Fixes these runs suggest, ranked

1. **Ask for the checkpoint before the reading crosses the mark, not after.**
   A lead that reads large files crosses the 120k–150k band in a single
   response, so the meter never sees a reading inside it (run 4:
   119,904 → automatic compaction).
   - Ask when the current reading plus the last response's growth reaches
     `checkpointAt`.
   - Or: when the post-compaction card finds no checkpoint for the epoch
     that just ended, ask the lead to write one from the summary.
2. **The Stop hook's "not committed" check needs two fixes.**
   - Do not fire when the last message already names every uncommitted path.
   - Never let the retry replace the report in headless mode. In run 1 the
     one-line answer became the run's `result`, so a scripted caller lost
     the summary.
3. **Stop what you started.** Servers were left listening in run 0 (:3000)
   and run 3 (:3999 from the helper, :4321 from the lead). Add one line in
   the card or the implementer's packet: stop, by process id, any server you
   started before you hand back or finish.
4. **Helper worktree hygiene.** In run 3 the implementer left its work
   uncommitted in the worktree and the lead copied files by hand.
   - The implementer should commit on its branch.
   - The lead should merge, then use `git worktree remove` without `--force`
     and `git branch -d`. The guard already allows that pair.
   - Say so where the dispatch reference describes `worktree: yes`.
5. **The "will wait for an independent review" tag.** In run 0 the word
   "contract" in a packet triggered it. No review was sent and nothing
   waited. Either enforce it at finish or drop the promise from the tag.
6. **Say WHERE in the first packet.** Run 0 lost three dispatches to the
   worktree refusal. The dispatch reference's packet template could carry
   `worktree: yes` for implementers by default.
7. **The meter's window figure** should follow `CLAUDE_CODE_AUTO_COMPACT_WINDOW`.
   This is cosmetic; it is carried over from round 8.
