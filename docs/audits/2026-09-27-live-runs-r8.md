# Live runs — round 8, four scenarios the earlier rounds never reached (2026-09-27)

Rounds 4 to 7 all ran one delivery prompt: the tool-library app in three
parts, each handed to a helper. They never exercised the parts of the plugin
that only fire under pressure: a dispatch the guard must redirect, a helper
that runs out of turns, a conversation that is compacted mid-task, a lead that
must find requirements hidden in a long document. Round 8 runs four prompts
built to reach each of those, against the audit branch at `7d62e2b` (waves 7 to
9 up to the README change landed; the two fixes that came out of this round,
`e917eea` and the per-segment turn count, landed after it).

## Method

Same harness as rounds 4 to 7: the branch loaded with `--plugin-dir` from a
detached worktree pinned at `7d62e2b` with both skill packages built (77 files
each), the installed copy disabled for the child with
`--settings '{"enabledPlugins":{"orchestrate@orchestrate":false}}'`,
`--model sonnet` (Claude Sonnet 5, 1M-token window), headless `-p`,
`--output-format stream-json --verbose`, `--max-budget-usd 10`, default
permission mode. Claude Code 2.1.274. One fresh throwaway repo per run under a
short temp path, deleted after this write-up. Raw streams, the app's own
session transcripts and the helper transcript are kept in the session scratch
folder (not committed: machine paths).

Two things were staged, and both are disclosed because they change what the
numbers mean:

- **The implementer's turn cap was lowered from 100 to 20** in the live
  worktree's copy of `agents/orch-implementer.md` only (never committed), so
  that run 3 would hit the cap inside a $10 budget.
- **Runs 2 and 4 set `CLAUDE_CODE_AUTO_COMPACT_WINDOW=100000`** in the child's
  environment so that a compaction would happen inside one sitting.

Settings file: modification time identical before and after all four runs (the
same 12:25:42 stamp as rounds 4 to 7). Nothing on this branch touched the real
profile. A separate clean-profile install into a throwaway home succeeded and
is described at the end.

The four prompts, in one line each:

1. **Requirements, one file at a time.** Build the app; first hand a helper the
   31 short requirement files in `docs/requirements` to read one at a time and
   report any two that contradict; keep a `notes.txt` of anything not done;
   the user cannot answer questions.
2. **Hidden requirements in a long spec.** Build the app from a 12,000-line
   `docs/spec.md` in which four numbered paragraphs marked as binding are not
   findable by searching for the marker word.
3. **One helper for the whole build.** Hand the complete build to a single
   helper in one go; review what comes back, fill gaps, run the tests, commit,
   and report honestly what the helper did and what it cost.
4. **Twelve meetings, one decision each.** Read the minutes of twelve meetings
   in `notes/`; some settled a decision about the website, some did not; write
   `DECISIONS.md` with one line per meeting, "Nothing decided" where nothing
   was, and commit.

## What the hooks did

**Run 1.** The lead's first dispatch went to the built-in general-purpose
agent. The dispatch guard refused it with:

> orchestrate workers: general-purpose has no turn cap and can start helpers of its own. Send a capped role agent instead: orch-implementer (model …

The lead sent the researcher role next, got the contradiction back, and built
the app itself. The guard's price tag fired on each dispatch, and its
"no PROGRESS line: a capped return will have nothing to resume from" warning
fired three times for a short read-only helper, where it is noise.

**Run 2.** No helper, no compaction. The lead searched the spec by structure
(numbered paragraphs) rather than by the marker word, found all four hidden
requirements, and implemented them. It started the server in the background to
check it and **never stopped it**: the process was still listening on port
3000 when run 3 began, and run 3's helper hit "address in use" on its first
test until it found and killed the right process by id. Nothing in the plugin
tells the lead to stop what it started.

**Run 3.** The lead handed the whole build to one implementer in the
background. The helper ran to its (lowered) 20-turn cap mid-build. What
happened next is the round's main finding:

- The plugin's stop hook **did not fire** when the background helper stopped
  at its cap. Claude Code itself told the lead, in a task notification:
  "stopped at its 20-turn limit (partial result; SendMessage to task-id to
  continue)".
- The plugin's rule said the opposite ("Do not resume the stopped helper";
  SKILL.md: "never keep resuming a large helper"), but that note is emitted
  from the stop hook's return record, so it never reached the lead at the cap
  moment.
- The lead followed the host's advice and sent one message. The helper
  finished in 8 more turns, committed, and handed back. The stop hook then
  fired once, for the whole 28-turn transcript.
- The plugin counted all 28 turns, called 28 ≥ 20 "capped", **marked a
  finished return PARTIAL** and wrote "stopped at its 28-turn cap" (the cap
  was 20; 28 was the turn count). The lead saw "[orchestrate · partial]
  stopped at the turn cap, so partial: orch-implementer (28 turns)" three
  times on later tool calls, for a helper whose work was complete.

Also in run 3: the helper tried to clear port 3000 by ending every Node
process on the machine by name. The command guard refused it with:

> This would end every running program with that name on this machine, not only the one you started, including other people's servers and sessions. A background helper cannot ask, so this is refused: …

The helper then found the one process by id and ended only that. This is the
miss round 6 recorded, now caught live for the first time. After the merge the
lead tried to delete its helper's worktree branch with a forced branch delete
and the guard refused that too ("This would permanently delete a branch. You
are in auto mode, where nobody can say yes, so this is refused"), leaving a
stray branch and a `.claude/` folder in the user's repo.

**Run 4.** Two automatic compactions inside 19 turns (the transcript records
them at 173,139 → 21,068 tokens and 156,099 → 7,987 tokens). The plugin's
compaction gate blocked the first attempt because no checkpoint existed, then
allowed the next attempt for the same context state, as designed. **The block's
reason never reached the lead.** Under automatic compaction Claude Code shows a
PreCompact block reason to nobody: the lead's transcript has no trace of "write
a checkpoint first", so no checkpoint was written and the block only delayed
compaction by one step. The post-compaction card did arrive after each
compaction ("[orchestrate · after compaction] … Compaction 1 of this session. 0
helpers sent so far"), and the work survived both: all twelve lines of
`DECISIONS.md` are right, including the "Nothing decided" evenings, and the
lead's final message flagged the one decision the minutes left ambiguous. The
context meter said "~200k" as the window although the child's window was set to
100k, and the compactions came at 173k and 156k, so the meter's window figure
does not follow the override.

## The findings

1. **Cap detection counted the wrong thing.** Turns across the whole
   transcript, when a resumed helper's transcript holds two segments. Fix: count
   turns since the last user message that carries text (a resume appears as
   one), in the ledger, the running-helper count and the size notice; word the
   note with the cap, not the turn count. Landing after this round, with the
   scrubbed run 3 helper transcript as a fixture
   (`skills/orchestrate/scripts/fixtures/resumed-helper-transcript.jsonl`, 28
   turns in segments of 20 and 8).
2. **The resume rule contradicted the host and itself.** SKILL.md already
   says: message the agent while its cache is warm, otherwise a fresh packet.
   The "never resume" sentences a few lines later, the partial note and the
   dispatch reference said never. The advisor's call, taken: one shorter
   sentence that points back to the warm-cache rule, in all three places, and
   no new size number. The host's own notification already tells the lead
   about the cap, so a second note from the plugin was dropped as a duplicate.
3. **The stop hook is not the moment a background helper is capped.** Recorded
   as a fact about Claude Code 2.1.274, with the SubagentStop input fields
   (agent_id, agent_type, agent_transcript_path, last_assistant_message, no
   tool_use_id). The Agent tool's own PostToolUse result carries `agentId` and
   `status`, so `e917eea` pairs a dispatch with its return there instead.
4. **The compaction gate's reason is invisible under automatic compaction.**
   The gate can only delay by one step. What the lead does see is the
   checkpoint notice the meter raises before the compact mark, so that notice
   is where the checkpoint has to be asked for; the gate's reason text serves
   the manual `/compact` case only. Not changed in this round; recorded in the
   run ledger for the next.
5. **Nothing tells the lead to stop what it started.** One line for SKILL.md
   or the card when bytes allow; recorded, not changed.
6. **Helper worktree branches cannot be cleaned up in auto mode.** The guard
   refuses every branch delete. Landing after this round: the unforced delete
   (the form git itself refuses when the branch is unmerged) is allowed for
   `worktree-agent-*` branches only; the forced delete stays refused for every
   branch.
7. **The meter's window figure ignores the override.** Cosmetic here, since
   the compact-mark advice still fired; recorded.
