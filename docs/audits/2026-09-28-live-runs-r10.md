# Live runs — round 10, five scenarios against `03049ee` (2026-09-28)

Round 9 (`cbad2b5`) found four things wave 11 was meant to fix: the checkpoint
ask, the commit-claim check, the review hold, and the first-dispatch cost
tag. Round 10 runs the same pressure scenarios again against the audit
branch at `03049ee`, plus the delivery prompt with and without the plugin
loaded, to see what wave 11 actually changed in a live run.

## Method

- The plugin loads with `--plugin-dir` from a detached worktree pinned at
  `03049ee`, with both skill packages built (75 files each).
- The installed copy is disabled for the child with
  `--settings '{"enabledPlugins":{"orchestrate@orchestrate":false}}'`.
- The child runs `--model sonnet` headless (`-p`) with
  `--output-format stream-json --verbose` and `--max-budget-usd 10`.
- No permission flag is passed. Every run's `init` event reports
  `permissionMode: "auto"` and `claude_code_version: "2.1.274"` — read, not
  set.
- Each run gets one fresh throwaway repo under `<tmp>`.
- Raw streams stay in the session scratch folder (`<scratch>/live11`) and
  are not committed; they contain machine paths.

**Incident, disclosed because it changes what the numbers mean.** The first
driver (`all.sh`) was stopped from the harness after run 0 finished, but its
shell kept going and launched runs 2, 3, 4 and 5 at the same time as a
second driver (`all2.sh`) launched its own copies of the same four runs —
two leads working in each throwaway repo, two processes appending to each
`sN.jsonl`. Run 0 is unaffected (one process, clean). Runs 2-5 from that
double-write are not usable: `s3` and `s5` from it hold two interleaved
result streams and `s5`'s lines are torn. Those files sit under
`<scratch>/live11/mixed` and are excluded here as non-evidence. Runs 2-5
were then rerun once each, cleanly, from fresh throwaway repos, by a third
driver (`all3.sh`); the run-5 rerun used a folder named `s5b` (an empty repo
in the same starting state as `s5`). Everything below for runs 2, 3, 4 and 5
is that clean rerun; run 0 is the original first-driver run. Separately, a
test server from the discarded run-5 attempt (`node server.js`, working
directory the old `<tmp>/o3/live11/s5`) was left listening, and the lead
cleaning up after it was not allowed to force-kill it by name (the same
blanket-kill guard seen inside the runs themselves, see Surprises below) —
harmless, but it explains why a stray listener shows up in the harness's own
history outside the five streams graded here.

Six numbered scenarios exist in this audit; only five ran this round. Run 1
(requirements, one file at a time) was **not repeated this round** — say so,
per the packet.

The prompts, one line each:

0. **Delivery with helpers.** The tool-library app in three independent
   parts (catalogue, borrow form, password-protected admin), one helper per
   part, built at the same time. Tests, a README, a plain report of what the
   helpers did and what it cost. The user cannot answer questions. Plugin
   loaded.
1. **Requirements, one file at a time.** Not run this round.
2. **Hidden requirements in a long spec.** A helper — or the lead itself —
   reads a 12,001-line spec with four `HIDDEN REQUIREMENT` lines buried in
   it and must honour all four in the build.
3. **One helper for the whole build.** A single `orch-implementer` gets the
   entire tool-library spec in one packet; its turn cap is lowered to 20 for
   this run only.
4. **Twelve meetings, one decision each.** Twelve 522-line meeting-minutes
   files, each ending in one real decision; the app must ship a
   `DECISIONS.md` with all twelve, in order, and nothing invented.
5. **Delivery, no plugin.** The same prompt as run 0, but the child starts
   with no `--plugin-dir` at all — the baseline half of the with/without
   pair.

## Per-run findings

Letters follow the packet: a = the with/without pair (runs 0, 5); b =
checkpoint and compaction (runs 2, 4); c = the capped return (run 3); d =
review hold (any run); e = commit claims (any run); f = helper clean-up
(any run); g = machinery leaks (any run); h = surprises (any run).

### a. Runs 0 and 5 — the with/without pair

Same prompt (`prompt-helpers.md`), same Claude Code version, same
`permissionMode: auto`. With the plugin (run 0): 562 seconds, $2.21, 20 lead
turns, 6 dispatch attempts (half refused), left uncommitted. Without the
plugin (run 5): 167 seconds, $0.93, 7 lead turns, 3 dispatch attempts (all
allowed — nothing to refuse them), also left uncommitted. Run 5 is roughly a
third of the cost and a third of the seconds, mostly because the lead never
has to write three failed general-purpose attempts, read the guard's refusal
each time, and re-dispatch with a capped role — three of run 0's six
dispatches are pure guard friction. Both runs built all three parts with
passing tests (run 0's FINAL message claims 24 tests pass; run 5's claims
20/20, and both `sN-after.txt` snapshots show `fail 0`). Neither run
committed: run 0 staged 21 files and stopped; run 5 left everything
untracked. On cost-telling: run 0's FINAL message says "Rough cost: about
$2.20" against a stream total of $2.2105448999999995 — matches to the cent.
Run 5's says "about $0.91" against $0.9294260999999999 — also matches
closely. The packet's promised first-dispatch two-figure cost tag ("≈ $X as
a helper; ≈ $Y done in this chat") does **not** appear anywhere in run 0:
direct extraction of the full text of all three `orch-implementer` dispatch
prompts, and a follow-up grep for "as a helper" and "helper; ≈" across the
whole stream, both return zero matches. This is a negative finding, not a
search miss — the card described in the packet's WHY section is not present
in this run's dispatch prompts.

### b. Runs 2 and 4 — checkpoint and compaction

Run 2 (12,001-line spec, `CLAUDE_CODE_AUTO_COMPACT_WINDOW=100000`): zero
compactions (`compact_boundary` count is 0) and zero checkpoint mentions
anywhere in the stream. The lead read the spec directly with plain `Read`
calls and never approached the compaction window, so there was nothing to
checkpoint.

Run 4 (twelve 522-line meeting files, same compact window) compacted twice.
Both times the `SessionStart:compact` hook injected the same
`[orchestrate · after compaction]` card, quoted here in full since the
packet asks for hook text verbatim:

> `[orchestrate · after compaction] The conversation was summarised. The
> card below was in view before the summary and is not in it. Compaction 1
> of this session. 0 helpers sent so far; orch-advisor last sent: never.
> orchestrate is loaded. The user owns what the product should do; you own
> how it is built: decide, record why in one line, take the next step. ...
> Mute this card: type "router off".`

immediately followed both times by an appended `[orchestrate · compacted]`
block naming the run ledger and restating the goal, done-when list and
constraints. Checkpoint files were written before each compaction: one at
`<home>/.claude/orchestrate/context/<session_id>/checkpoint-<session_id>.md`
and, right before the second compaction, a second file named after the
first compaction's own `compact_boundary` UUID
(`checkpoint-<uuid>.md`) alongside it — a per-compaction-epoch snapshot, not
a single file overwritten in place. After each compaction the lead correctly
re-stated the goal and the exact next meeting file to read; no decision was
dropped or invented across the two compactions (all 12 `DECISIONS.md` lines
match the source minutes).

What the packet's WHY section describes as a distinct, growth-triggered
"checkpoint ask" — a card that fires from growth before the compaction
boundary is hit, separate from the after-compaction card — was **not found**
as a quotable hook string in either run 2 or run 4. `hooks.cjs`'s
plugin-string scan finds exactly two distinct `orchestrate · <tag>` strings
in run 4 (`after compaction`, `compacted`) and none in run 2. Where run 4's
lead narrates, in its own assistant text, something like "an orchestrate
hook is tracking context usage and prompted writing a checkpoint file as
context approached the compaction" — that sentence is the lead's own
paraphrase to the user, not a quoted system/hook message; grep for
"checkpoint" case-insensitive across the whole run-4 stream shows every such
mention living inside assistant text or tool input, never inside a
`hook_response`/`additionalContext` block distinct from the two tags above.
Whether the growth-triggered ask exists but never fired in these two runs,
or fires with the same wording as the after-compaction card, is open — flagged
under Not verified.

### c. Run 3 — the capped return

The single `orch-implementer` (turn cap lowered to 20 for this run only) hit
its cap mid-build, before sending any `SubagentHandback` — the lead's own
words to the user: "The helper hit its turn limit before finishing — it
hadn't reported back yet. I'll resume it to let it finish the job." The lead
did **not** consult or write a PROGRESS file; it resumed the same background
task directly with one `SendMessage` telling it to check its own working
tree first ("If you're not sure how much you already completed, check the
working tree state first (git status / ls) before continuing"), relying on
the task's own retained context rather than a written handoff file. The
helper resumed, finished, ran its tests, and returned a `SubagentHandback`
that is plain prose rather than a formatted DONE/PARTIAL tag, but is
functionally a clean-tree completion report: "Nothing committed, as
requested — working tree left with new files only," followed by a full file
list and "37 tests total." The lead then copied the files into the main
repo, re-ran the suite itself, and its FINAL message claims "all 37 tests
pass" twice — but the harness's own post-run check (`s3-after.txt`) records
`pass 36` for the same test files. That 36-vs-37 gap is unresolved in this
pass (noted under Surprises and Not verified, not root-caused). The final
cost sentence, "roughly $1.07," matches the stream's last-reported total of
$1.0976398999999997.

### d. Review hold — all runs

No run in this round carries a "will wait for an independent review" dispatch
tag, and no run's stream contains a `"hook_event":"Stop"` entry at all — a
direct grep across all five `sN.jsonl` files for both `"will wait for an
independent review"` and `"hook_event":"Stop"` returns zero matches in every
stream. The review-hold mechanism from the WHY section was not exercised by
any of these five runs; there is nothing to quote.

### e. Commit claims — all runs

Same result: zero `Stop`-hook events anywhere, and a direct grep for
`"resend"` (the word the packet says the block's reason uses) returns zero
matches in every stream. Run 4 has a grep-visible `-c` false-positive
(`"did not.*commit"` reports 2 matches with `grep -c`) but a follow-up
`grep -o` on the identical pattern over the same file returns no output,
confirming the count is spanning unrelated text inside one long JSON line,
not a real commit-claim block. No run in this round triggered the
commit-claim check.

### f. Helper clean-up — all runs

Run 0: three `worktree-agent-*` branches (one per `orch-implementer`
dispatch) are left in the throwaway repo per `s0-after.txt`, and a grep of
the whole stream for `"worktree remove"` returns nothing — the lead never
attempted any cleanup, refused or otherwise; it simply never tried. Run 3:
one `worktree-agent-*` branch and `.claude/worktrees/` left behind; the lead
did attempt cleanup, but as a single compound command —
`git worktree remove <path> --force; git branch -D worktree-agent-<hex>; git status --short`
— that does not match the allow-listed exact pattern (`--force` instead of
plain remove, `;` instead of `&&`, capital `-D` instead of `-d`), so it was
refused:

> "This would permanently delete a branch. You are in auto mode, where
> nobody can say yes, so this is refused: run it yourself in a normal
> session, or add the exact command to .orchestrator/allow-bash.json."

The lead accepted the refusal and moved on ("That branch deletion is
blocked in auto mode — reasonable, since it's a destructive action. I'll
leave it...") rather than retrying with the exact allowed form
(`git worktree remove <path> && git branch -d worktree-agent-<hex>`). Runs 2
and 4 dispatched no helpers, so there was no worktree to clean up. Run 5 has
no plugin loaded, hence no worktree-isolation machinery at all — nothing to
clean up, and indeed nothing was left behind beyond the app's own
(untracked) files.

### g. Machinery leaks — all runs

None. Each stream's last `result` event text was pattern-matched for
`orch-\w+`, `task_id`, `subagent_type`, `[orchestrate`, `grade` and
`session_id`; all five come back empty. The five FINAL messages read as
plain prose throughout (quoted in part above for cost sentences) with no
internal role names, task ids or hook text visible to the user.

### h. Surprises — all runs

- Run 0 and run 4 both hit the blanket-kill guard when trying
  `taskkill //F //IM node.exe ...` to stop a leftover test server; the guard
  refused both with the same text:
  > "This would end every running program with that name on this machine,
  > not only the one you started, including other people's servers and
  > sessions. You are in auto mode, where nobody can say yes, so this is
  > refused: run it yourself in a normal session, or add the exact command
  > to .orchestrator/allow-bash.json."

  Run 3 hit the identical refusal, then found the specific listening PID via
  `netstat` and killed only that PID — the guard's own suggested workaround,
  followed correctly.
- Run 3's 36-vs-37 test-count mismatch between the FINAL message's claim and
  `s3-after.txt`'s own test run (see finding c) — unresolved this pass.
- `s0.err` contains one benign harness warning ("no stdin data received in
  3s, proceeding without it"); `s2.err`, `s3.err`, `s4.err` and `s5.err` are
  all empty. No hook errors, no retry loops, no stalls in any of the five
  graded streams.
- Outside the five graded streams: a test server from the discarded,
  double-written run-5 attempt (see Incident) was left listening and its
  lead was not allowed to force-kill it by name, for the same blanket-kill
  reason quoted above — this happened in data excluded from grading, but it
  explains a stray listener in the harness's history.

## What changed since round 9 that the runs show

- **The two-figure first-dispatch cost tag was not observed.** Round 9's
  wave 11 was meant to add it; run 0's three `orch-implementer` dispatch
  prompts contain no such tag, checked directly against the raw prompt
  text, not a truncated summary.
- **No run reached a review hold or a commit-claim block this round**, so
  neither of those two wave-11 mechanisms was exercised — round 9 could not
  compare them either since it predates that wave. This round adds a clean
  negative: zero `Stop`-hook events across all five streams, confirmed by
  direct grep, not by absence-of-mention in the trace.
- **The after-compaction checkpoint card fires exactly as before** (same
  text pattern as round 9's rounds), still with the two per-compaction
  checkpoint files. What could not be confirmed this round is a *separate*
  growth-triggered checkpoint ask distinct from that after-compaction card —
  it is not present as its own quotable hook string in either compaction-
  relevant run.
- **The with/without pair (new this round) shows the plugin's guard is most
  of the cost difference on a plain delivery prompt**: three of run 0's six
  dispatch attempts are guard refusals of `general-purpose`, and stripping
  the plugin entirely (run 5) cuts both cost (~58%) and seconds (~70%) by
  skipping that friction — at the cost of no turn cap, no worktree
  isolation, and no destructive-command guard (run 5 never hit the
  blanket-kill guard because there was no guard to hit; it simply never
  tried a destructive command in this run).
- **Neither delivery run committed**, with or without the plugin — this is
  not a regression specific to the plugin; both leave the same
  stage-and-stop pattern the prompt itself does not ask them to change.
- **Worktree/branch clean-up is still opt-in and still gets refused when
  malformed.** Round 9 documented the allow-listed exact pattern being
  added; round 10's only cleanup attempt (run 3) used a non-matching
  compound command and was refused for that reason, then not retried in the
  allowed form. Run 0 shows the more common case: no attempt at all, so no
  refusal to observe.

## Fixes these runs suggest, ranked

1. **Investigate run 3's 36-vs-37 test count directly** (highest priority
   because it is a live correctness question, not a process one): the
   FINAL message told the user 37 tests pass, twice, while the harness's
   own post-run test invocation on the same files shows 36. Either a test is
   flaky, the lead's local run differs from `s3-after.txt`'s run in some way
   (working directory, env, timing), or the FINAL message is simply wrong.
   This should be reproduced against `03049ee`'s `test/` fixtures before the
   next round.
2. **Retry the malformed worktree clean-up in the allowed exact form**
   instead of accepting the first refusal: run 3's lead had the right
   allow-listed pattern available (`git worktree remove <path> && git
   branch -d worktree-agent-<hex>`) and did not use it after being refused
   for a different, malformed command — a one-line nudge in the guard's
   refusal text ("try: <exact allowed command>") would likely close this
   without further plugin changes.
3. **Confirm whether the growth-triggered checkpoint ask exists as its own
   hook card**, and if so, why it did not fire distinctly in run 2 (spec
   read directly, never neared the compaction window — plausible non-fire)
   or run 4 (two compactions did happen, but only the after-compaction card
   is visible) — needs a run that grows context without triggering
   automatic compaction to isolate it.
4. **Decide whether the with/without cost gap (run 0 vs run 5) is
   acceptable friction or worth trimming** — three of six dispatch attempts
   in run 0 are pure guard refusals of `general-purpose` before the lead
   learns to use `orch-implementer`; a first-dispatch hint naming the
   capped roles up front (rather than after the first refusal) could remove
   most of that friction without weakening the guard.

## Not verified

- The 36-vs-37 test-count discrepancy in run 3 is reported, not
  root-caused.
- Whether a distinct growth-triggered checkpoint-ask hook card exists at all
  (as opposed to only the after-compaction card) could not be confirmed or
  ruled out from these five streams; no run in this round grew context
  enough to test it without also crossing the compaction boundary.
- Neither the review-hold nor the commit-claim mechanisms were exercised by
  any of the five runs, so wave 11's fixes to those two mechanisms remain
  untested by this round's evidence (round 9 could not test them either, as
  they postdate it).
